# Legacy set conversion experiment

Some old Live sets contain a binary document instead of compressed XML. The experimental reader decodes the AB1E dialect found in the Suite 8 sets we inspected and converts a set to XML.

```python
from pathlib import Path
from abletoolz.experimental.legacy import convert_file

result = convert_file(Path("old.als"))
song = result.live_set
print(result.report.warnings)
```

Like any abletoolz save, this converts the set in place: the original is copied to `abletoolz_backup` first, and `abletoolz undo` puts it back. To write a new file instead, pass it: `convert_file(Path("old.als"), Path("converted.als"))` leaves the original alone and refuses a destination that already exists. The output uses the `8.2_260` schema and a synthetic target Creator header; it is generated by abletoolz, not saved by Live.

One converted set, a Live 8 demo with follow-action clips, opens and plays in Live 12 without complaint; others have not been opened yet. Device values are preserved as stored, but some binary values need conversion into the units XML uses. Product metadata is retained under its legacy names because its newer representation is unresolved. Relative media paths can need relinking when the output moves to another folder. The returned set finds its project folder from the destination, so relinking it with collection copies samples there, never into the original project.

The returned `AbletonSet` supports XML parsing and serialization. Track operations that require later fields such as `Name/EffectiveName` and `MasterTrack/DeviceChain` still need a later layout. This experiment does not enable automatic legacy loading through the normal constructor.

That set's 17 session clips, two groove clips, 192 notes, device nesting and modulation references survive XML readback. The decoder reads all 39 old files tried, Ableton's own Live 8 library sets among them, but most still stop on device fields not mapped yet, such as Simpler's and EQ Eight's. Private sets and generated candidates are not distributed as test fixtures; the committed tests build synthetic binary documents.

## What the old format stores

The observed files begin with `ab 1e 56 78`, followed by a dialect byte, another header word, a root type and a table of class definitions. Each class has a name, a revision and an ordered list of named, typed fields. Those definitions describe how to read the object values that follow.

Tracks, clips, devices and automation appear as nested records, lists and arrays. Numbers use explicit binary types; text is UTF-16LE; some fields hold opaque bytes. Persistent IDs connect references to their targets. A class revision is a serialization revision, not a Live release number.

This looks like Ableton's own versioned object serializer. The file itself exposes enough structure to decode it without guessing byte offsets for every device. We have not established its internal implementation or whether Ableton built it on another serialization framework.

The later XML files expose much of the same musical object model as tags and attributes. Converting between them still requires field renames, structural changes and value-unit mappings. Successfully reading the bytes is only the first part of recovering the set.
